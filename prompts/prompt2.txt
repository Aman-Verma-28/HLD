E.g.:
1. Deep Dive 1: Driver Accept/Decline (prevent double assignment)
-> Driver sees ride request: Push notification received, app shows ride details and clicks 'Accept' or Decline or timeout.
-> Interactions:
    -> Driver Service: Updates driver status to OFFER_PENDING in Redis (Using Redis Lock so that only one driver can be offered to a ride)
    -> Notification Service: Sends offer with 10–15s TTL
    -> Trip Service: On accept → transitions ride state via Trip Service; on decline/timeout → releases the reservation and tries the next candidate.
-> Why critical: Without this, a popular driver in a busy zone could be simultaneously offered to 5 ride requests. 
If two riders' apps both showed "matched" → angry users, support tickets, and a bad press cycle. The correctness here is the entire product's reputation.
-> Alternatives + trade-offs:
    -> Alternative 1: Use a database to store the driver status and ride request. (Using Postgres CAS so that only one driver can be offered to a ride)
    -> Alternative 2: Use a queue to store the driver status and ride request. (Using Kafka so that only one driver can be offered to a ride)
    -> These approaches fail because they are not atomic.
-> Recommendation: Use Redis Lock so that only one driver can be offered to a ride.
    -> Trade-off: Using Redis Lock is not as scalable as using a database or queue. But it is faster than using a database or queue.
